# Adapter probe lifecycle

The adapter consumes the reviewed upstream ab-av1 revision pinned in the [engine manifest](../crates/crfty-engine/Cargo.toml). The pinned ab-av1 adapter uses asynchronous, contained ffprobe work at search and encode entry and after each encoded sample. These probes need frame-rate and pixel-format facts absent from CRFty's durable `VideoMeta`, so the adapter cannot reconstruct their complete input from an earlier metadata observation. The selected executable remains the session's configured ffprobe path; neither a PATH lookup nor a second tool-selection policy is introduced.

## Bounds and cancellation

Each ffprobe is registered through the dependency's managed child path before its output is awaited. It runs in a Unix process group or a Windows Job Object; Windows creation retains the no-window flag. Its probe deadline is 30 seconds, stdout retains at most 1 MiB of JSON, and stderr retains at most a 4 KiB UTF-8 diagnostic tail. Oversized JSON fails rather than parsing a truncated document. Both pipes are drained concurrently, and the deadline is checked before each output chunk so continuous traffic cannot starve it. The timer ordering follows [Tokio's select fairness contract](https://docs.rs/tokio/latest/tokio/macro.select.html#fairness).

Entry probes participate in the adapter's cancellation race before the command update loop begins. Encoded-sample probes await inside that loop, so cancellation can drop their future and proceed to job finalization. Dropping a probe future leaves its child registered; the adapter reports cancellation only after registered group termination and direct-child wait complete. A timeout or capture/read failure settles that probe's group before returning its failure.

Leader exit does not establish that its containment unit is empty. The output stream observes leader exit alongside pipe reads, before requiring pipe EOF. Completion polls the inner child under a short mutex guard, releasing the guard before waiting between polls so cancellation can acquire termination authority. It then requests group termination and waits for the direct child before finishing pipe drainage. Failed-job finalization also requests group termination when the leader's status is already available. This covers descendants that retain inherited pipes and descendants that close them. Unix guarantees a group termination request and direct-child reap, rather than reaping arbitrary grandchildren. Windows also invokes the dependency's Job wait, whose completion notifications do not independently prove descendant exit; the [containment contract](PROCESS_CONTAINMENT.md) records that limit. An already-empty group is accepted, while other exposed termination and wait failures remain observable. Settled registrations are retired, and settlement is idempotent; later cancellation cannot signal their expired Unix process-group IDs.

Image classification comes from the same bounded ffprobe JSON. The dependency does not open or sniff the media file locally, so a named pipe cannot strand a blocking filesystem task before the deadline or during runtime shutdown.

## Failure evidence

The dependency reports unavailable, timed-out, rejected, invalid-output, and supervision failures as typed probe errors. Rejection preserves an available exit code. The adapter maps those kinds to its own boundary types and retains a bounded diagnostic separately from the contextual message. Lossy decoding cannot expand the retained text beyond its byte cap. Process cleanup and later job-finalizer failures preserve the initiating probe kind, message, and diagnostic rather than converting them into plain cancellation or a generic error.

Probe failures are independent of the requested hardware decoder. They end the failed phase without retrying the same probe under software decoding or descending through the quality-target ladder. Search and encode failures caused by their actual decode work retain the existing hardware-to-software retry behaviour. The dependency substitutes the exact probed path with `<probe-input>` across read boundaries before capping stderr, including generated sample paths. The adapter also applies its capture-time scrubbing before constructing the durable diagnostic tail, so terminal SearchRun and EncodeRun failure facts do not expose that path.

## Executable coverage

The `adapter_probes` integration suite uses separate native fixture processes so the dependency's global child and temporary registries cannot leak between concurrent tests. An outer supervised deadline bounds each fixture. Configured fake FFmpeg and ffprobe executables run with an empty PATH directory, proving that the configured tool paths remain effective. A descendant heartbeat signals probe readiness before cancellation; post-settlement checks verify that it stops and that the direct probe process has disappeared.

The suite covers search and encode entry cancellation, encoded-sample cancellation, initial and sample-probe timeout, an exited leader with inherited-pipe descendants, completed probes with closed-pipe descendants, rejected probes with noisy stderr, invalid JSON, and oversized JSON. Unix cases also cover live leaders with closed pipes and named-pipe input, including timeout, cancellation, and runtime shutdown. Every case then completes another search and encode in the same adapter runtime. Pure tests cover diagnostic bounds, invalid UTF-8, typed contextual errors, and preservation of primary and cleanup failures. The repository's Windows and Linux Rust jobs run these process contracts.

These probe guarantees do not replace the complete owned-operation lifecycle selected by [ADR-021](adr/021-drive-ab-av1-through-an-owned-operation.md). The dependency still uses its current single-job global registries and sample producer; [ADR-018](adr/018-unify-job-cancellation-and-completion.md) owns the engine's pending supervision unification. The [containment contract](PROCESS_CONTAINMENT.md) records Windows failed-spawn ownership and application-exit cleanup.
